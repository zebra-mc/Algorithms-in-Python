# Задача 3. Heapsort

`heapsort(arr)` сортирует массив по возрастанию **на месте** и возвращает тот же список.
Сортировка использует самостоятельно реализованную maxheap и итеративное просеивание;
в `main.py` нет импортов, `heapq`, `sorted()`, `list.sort()` или вспомогательного массива
для результата. Пустой массив, один элемент и повторяющиеся ключи поддерживаются.
Ключи должны быть взаимно сравнимы и образовывать полный порядок.

## Идея алгоритма и корректность

### Этап 1. Построение maxheap

В задаче 1 строили minheap, где в корне находится минимум. Для сортировки по возрастанию
удобнее maxheap: родитель не меньше своих детей, значит в корне находится максимальный ключ.
Максимум можно сразу поставить на его окончательную позицию в конце массива, не выделяя
нового списка. Если делать то же с minheap, порядок получился бы убывающим.

Построение идет снизу вверх, от `n // 2 - 1` до `0`, как линейный `makeheap` из задачи 1,
но с обратным направлением сравнения. `sift_down_max(arr, root, size)` выбирает большего
ребенка и при необходимости меняет с ним родителя. `size` — исключительная правая граница
активной кучи; элемент с индексом `size` и все правее нее недоступны для просеивания.

**Корректность построения:** листья уже maxheap. При обработке очередного узла оба
поддерева детей исправлены, поскольку их индексы больше. После обмена с большим ребенком
свойство maxheap восстановлено в родителе, а нарушение возможно только в том поддереве,
куда опустился прежний ключ. Просеивание идет вниз до устранения нарушения. Следовательно,
после обработки корня `arr[:n]` — maxheap.

### Этап 2. Перенос максимума в конец

Для `end = n - 1, ..., 1` выполняются два действия:

```python
arr[0], arr[end] = arr[end], arr[0]
sift_down_max(arr, 0, end)
```

Максимум текущей кучи занял позицию `end`. Активная куча теперь находится в `arr[:end]`;
новый корень может нарушать ее свойство, поэтому его просеиваем вниз. Хвост `arr[end:]`
больше не участвует ни в одном последующем обмене.

**Инвариант:** перед итерацией с индексом `end`

1. `arr[:end+1]` — maxheap;
2. `arr[end+1:]` отсортирован по возрастанию и содержит наибольшие элементы исходного массива;
3. каждый ключ в куче не больше любого ключа в отсортированном хвосте.

После построения кучи хвост пуст, все три утверждения выполняются. Обмен переносит
максимум кучи в начало хвоста, не нарушая порядок хвоста (новый ключ не больше уже
извлеченных максимумов). В оставшейся части может нарушиться только свойство корня.
Просеивание исправляет его, не затрагивая хвост и не меняя состав активной части.
Тем самым все три условия верны для следующей итерации. В конце активная часть состоит
из одного, наименьшего элемента, а остальное уже отсортировано. Пустой и одноэлементный
массивы не требуют обменов. Все изменения — перестановки элементов исходного списка,
поэтому ни один ключ не теряется.

## Оценка сложности

Пусть `n = len(arr)`, сравнения и обмены ключей имеют постоянную стоимость.

- Построение maxheap снизу вверх — Θ(n). Направление сравнений не влияет на высоты
  поддеревьев. Как доказано в задаче 1, сумма высот всех узлов равна
  `sum_{d=1}^{floor(log2 n)} floor(n / 2^d) < n`.
- На втором этапе `n - 1` обменов корня с последним активным элементом и по одному
  просеиванию кучи размера `end`. Стоимость просеивания ограничена `O(1 + log end)`.
  Поэтому `sum_{end=1}^{n-1} O(1 + log end) = O(n log n)`.

**Время в худшем случае — Θ(n log n).** Верхняя оценка получена выше, нижняя следует
из общей границы Ω(n log n) для сортировок сравнениями в худшем случае на различных ключах:
дерево решений должно различать `n!` возможных порядков, поэтому его высота не меньше
`log2(n!) = Ω(n log n)`.

У данной реализации лучший случай Θ(n): например, на одинаковых элементах каждое
просеивание сразу завершается. На любом непустом массиве длины n ≥ 2 выполняется
линейное число итераций, поэтому быстрее Θ(n) этот алгоритм не работает. Для n = 0 и n = 1
время O(1).

**Дополнительная память — O(1).** Куча и отсортированный хвост занимают части одного
и того же списка, не копируются и не выделяются как срезы (запись `arr[:end]` в объяснении
обозначает диапазон индексов, а не операцию в сортировке). Просеивание итеративное;
вызовы не образуют рекурсивного стека. Сортировка неустойчива: например, два равных
ключа при последнем обмене меняются местами.

Визуализация вынесена в `trace_heapsort`, которая передает наблюдатель `visit` реальному
алгоритму и сама сохраняет снимки. Это диагностический режим с O(n²) времени и памяти
на снимки; обычный `heapsort(arr)` не создает их.

## Визуализация

Массив `[1, 4, 7, 9, 0, 3, 2, 1]`: повтор ключа, неполный последний уровень и просеивания
на обоих этапах. В первых четырех строках после начального состояния строится куча,
затем на каждом шаге ее размер уменьшается на один.

| Шаг | Действие | Активная часть | Отсортированный хвост |
|---|---|---|---|
| 0 | начало | `[1, 4, 7, 9, 0, 3, 2, 1]` | `[]` |
| 1 | sift_down_max(3) | `[1, 4, 7, 9, 0, 3, 2, 1]` | `[]` |
| 2 | sift_down_max(2) | `[1, 4, 7, 9, 0, 3, 2, 1]` | `[]` |
| 3 | sift_down_max(1) | `[1, 9, 7, 4, 0, 3, 2, 1]` | `[]` |
| 4 | sift_down_max(0) | `[9, 4, 7, 1, 0, 3, 2, 1]` | `[]` |
| 5 | обмен 0 и 7, просеивание | `[7, 4, 3, 1, 0, 1, 2]` | `[9]` |
| 6 | обмен 0 и 6, просеивание | `[4, 2, 3, 1, 0, 1]` | `[7, 9]` |
| 7 | обмен 0 и 5, просеивание | `[3, 2, 1, 1, 0]` | `[4, 7, 9]` |
| 8 | обмен 0 и 4, просеивание | `[2, 1, 1, 0]` | `[3, 4, 7, 9]` |
| 9 | обмен 0 и 3, просеивание | `[1, 0, 1]` | `[2, 3, 4, 7, 9]` |
| 10 | обмен 0 и 2, просеивание | `[1, 0]` | `[1, 2, 3, 4, 7, 9]` |
| 11 | обмен 0 и 1, просеивание | `[0]` | `[1, 1, 2, 3, 4, 7, 9]` |

При построении на шаге 3 ключ 9 поднимается с индекса 3 на индекс 1, а на шаге 4 —
становится корнем. На шаге 5 максимум 9 уходит на окончательную позицию 7; просеивается
только префикс длины 7. Дальше хвост растет и никогда не меняет уже поставленные ключи.
В конце получаем `[0, 1, 1, 2, 3, 4, 7, 9]`.

## Экспериментальное сравнение

Сравниваем `heapsort`, встроенную `sorted` и собственную рекурсивную `merge_sort` из ДЗ 6
(с исходным декоратором `timer`, без логирования). Методика та же, что в задаче 1:
CPython 3.13.5, Linux x86_64, один прогрев, семь повторов, медиана `perf_counter()`;
фиксированный seed = 7, одинаковые данные, циклическая смена порядка запусков.
Копия входа для каждого вызова и проверка результата находятся вне замера.
При этом все выделения памяти внутри `sorted` и `merge_sort`, а также небольшой накладной
расход декоратора `timer`, включены в измерение. Это сравнение трех реально используемых
функций, а не одинаковых по контракту сортировок: `heapsort` меняет свой аргумент,
а `sorted` и `merge_sort` возвращают новые списки.

### Выводы

- `sorted` оказался самым быстрым на всех исследованных входах. В CPython это оптимизированная
  реализация на C с адаптивным использованием упорядоченных участков массива; на возрастающих,
  убывающих и одинаковых данных преимущество особенно заметно.
- На случайных массивах `merge_sort` быстрее нашей реализации heapsort (при n = 100 000:
  около 202 против 333 мс). Это не противоречит одинаковой худшей асимптотике O(n log n):
  различаются константы, число операций и характер доступа к памяти. При этом `merge_sort`
  требует O(n) дополнительной памяти, а `heapsort` — O(1).
- На одинаковых ключах `heapsort` существенно быстрее `merge_sort` (около 29 против 120 мс
  при n = 100 000): просеивания останавливаются сразу, тогда как рекурсивное слияние из ДЗ 6
  все равно делит и сливает массив. Это согласуется с линейным лучшим случаем данной версии heapsort.

Абсолютные результаты зависят от окружения и нагрузки; таблица отражает проведенные замеры,
а не гарантированное соотношение производительности на любой машине.
