# Задача 1. Compare

Нужно реализовать рекурсивные mergesort и quicksort, декоратор для замера времени выполнения и
подобрать входы, на которых время работы этих сортировок заметно различается.

Обе сортировки возвращают **новый** отсортированный список и не меняют входной. Тот же интерфейс у
итеративных версий из задачи 2.

## Идея решения

### Декоратор timer

```python
@functools.wraps(func)
def wrapper(*args, **kwargs):
    start = time.perf_counter()
    try:
        return func(*args, **kwargs)
    finally:
        wrapper.last_time = time.perf_counter() - start
```

Время последнего вызова в секундах лежит в атрибуте `last_time` обертки, а не печатается: так
эксперимент может сделать несколько запусков и сам их обработать. Результат возвращается без
изменений, исключение пробрасывается дальше, а `finally` записывает время в обоих случаях.
`functools.wraps` сохраняет `__name__`, `__doc__` и дает `__wrapped__`.

Декоратор стоит на `merge_sort` и `quick_sort`, а рекурсия идет во вспомогательных `_merge_sort` и
`_quick_sort`. Если бы рекурсивной была сама декорированная функция, каждый вложенный вызов тоже
проходил бы через обертку: на `n` элементов добавились бы порядка `n` лишних вызовов
`perf_counter`, и замер искажался бы. Итог при этом остался бы верным (внешний `finally`
выполняется последним, это проверено тестом), но мерить лучше одну точку входа.

### Mergesort

`_merge_sort(nums)`: если элементов не больше одного, вернуть копию; иначе разделить на
`nums[:mid]` и `nums[mid:]` при `mid = len(nums) // 2`, отсортировать обе половины рекурсивно и
слить их функцией `merge`. `merge` идет двумя указателями и при равенстве берет элемент слева
(`<=`), поэтому сортировка устойчива. На слайде 20 при нечетной длине больше левая половина, здесь
правая: это не влияет ни на результат, ни на оценки.

### Quicksort

Как на слайдах 17-18: pivot - **последний** элемент отрезка, элементы меньше pivot переносятся
влево, остальные (больше **или равные**) остаются справа, после чего сортируются оба отрезка.
`quick_sort` один раз копирует вход, дальше все происходит на месте в этой копии.

```python
def partition(arr, low, high):
    pivot = arr[high]
    i = low  # arr[low..i-1] - уже найденные элементы меньше pivot
    for j in range(low, high):
        if arr[j] < pivot:
            arr[i], arr[j] = arr[j], arr[i]
            i += 1
    arr[i], arr[high] = arr[high], arr[i]
    return i
```

Для массива со слайда 18 `[9, -3, 5, 2, 6, 8, -6, 1, 3]` получается
`[-3, 2, -6, 1, 3, 8, 5, 9, 6]` и `p = 4`, то же разбиение, что на слайде (проверено тестом).

## Почему алгоритмы корректны

**merge.** Инвариант цикла: `result` - отсортированные `i` наименьших элементов `left` и `j`
наименьших элементов `right`, и каждый из них не больше `left[i]` и `right[j]`. Следующим
добавляется меньший из `left[i]`, `right[j]`, он не меньше последнего элемента `result`, поэтому
инвариант сохраняется. Когда одна часть кончилась, остаток другой отсортирован и не меньше всего
`result`.

**merge_sort.** Индукция по длине: части длины 0 и 1 отсортированы; при `n >= 2` обе половины
короче `n`, по предположению сортируются верно, а `merge` двух отсортированных списков дает
отсортированный список из тех же элементов.

**partition.** Инвариант перед итерацией `j`: `arr[low..i-1] < pivot`, `arr[i..j-1] >= pivot`.
Если `arr[j] < pivot`, обмен с `arr[i]` переносит его в левую часть, а элемент `>= pivot` - в
конец правой. В конце `arr[high]` меняется с `arr[i]`, первым элементом правой части. Итог:
`arr[low..p-1] < pivot = arr[p] <= arr[p+1..high]`.

**quick_sort.** После `partition` pivot стоит на своем окончательном месте: все левее меньше,
все правее не меньше. Отрезки `[low, p-1]` и `[p+1, high]` короче исходного на 1 и больше, поэтому
рекурсия конечна, а по индукции они сортируются верно.

## Сложность

### merge_sort

- Глубина рекурсии `ceil(log2 n)`, на каждом уровне срезы и слияния вместе обрабатывают все `n`
  элементов за O(n). Время **Θ(n log n)** в любом случае: даже на отсортированном входе меньше
  только сравнений в `merge`, а копирование срезов то же.
- Память: результат O(n). Рабочая память - срезы и результаты слияний на текущем пути рекурсии:
  `n/2 + n/4 + ...` для срезов и столько же для результатов, то есть O(n), плюс стек
  O(log n). Итого **O(n)**.

### quick_sort

`partition` на отрезке длины `m` делает `m - 1` сравнений и не больше `m` обменов.

- **Лучший и средний случай Θ(n log n).** Если pivot делит отрезок примерно пополам, уровней
  O(log n), на каждом O(n) работы. Для случайного порядка различных значений ожидаемое число
  сравнений около `2 n ln n`.
- **Худший случай Θ(n²)**, когда pivot каждый раз - минимум или максимум отрезка: один из отрезков
  пустой, второй короче всего на 1, сравнений `(n - 1) + (n - 2) + ... + 1 = n(n - 1)/2`. Для
  pivot = последний элемент это **отсортированный** и **обратный** массивы. К тому же приводят
  **одинаковые значения**: равные pivot уходят вправо, `p = low`, и справа остается `m - 1`
  элементов. Много повторов тоже делает разбиения сильно неравными: например, 20 000 случайных
  чисел из `0..3` уже дают `RecursionError`.
- **Память.** Копия входа (она же результат) O(n). Стек: обе части сортируются рекурсивно, поэтому
  глубина O(log n) при удачных pivot, но **до n - 1 кадров** в худшем случае. При стандартном
  пределе 1000 кадров отсортированный массив длиннее примерно 1000 элементов дает `RecursionError`
  (при запуске скрипта первая ошибка на длине 998, в тестах проверяется длина `предел + 100`). Как ограничить стек O(log n), показано в задаче 2.

## Пример работы

Массив с повторами `[5, 2, 7, 2, 9, 1, 2, 6]`. Все таблицы ниже напечатаны `python main.py`,

### merge_sort: дерево вызовов

Строка с отступом - вход в вызов и его часть массива; строка `a + b -> c` на том же отступе -
слияние в этом вызове после возврата из обоих детей.

```text
[5, 2, 7, 2, 9, 1, 2, 6]
  [5, 2, 7, 2]
    [5, 2]
      [5]
      [2]
    [5] + [2] -> [2, 5]
    [7, 2]
      [7]
      [2]
    [7] + [2] -> [2, 7]
  [2, 5] + [2, 7] -> [2, 2, 5, 7]
  [9, 1, 2, 6]
    [9, 1]
      [9]
      [1]
    [9] + [1] -> [1, 9]
    [2, 6]
      [2]
      [6]
    [2] + [6] -> [2, 6]
  [1, 9] + [2, 6] -> [1, 2, 6, 9]
[2, 2, 5, 7] + [1, 2, 6, 9] -> [1, 2, 2, 2, 5, 6, 7, 9]
```

### quick_sort: разбиения

Каждая строка - один `partition` в порядке выполнения; pivot после разбиения - в скобках. Вызовы
на отрезках длины 0 и 1 (`[0, 0]`, `[2, 1]` и т.п.) сразу возвращаются и в таблицу не попадают.

| Шаг | Глубина | Отрезок | pivot | p | Массив после partition | Дальше |
|---|---|---|---|---|---|---|
| 1 | 0 | [0, 7] | 6 | 5 | `5 2 2 1 2 (6) 9 7` | [0, 4], [6, 7] |
| 2 | 1 | [0, 4] | 2 | 1 | `1 (2) 2 5 2 6 9 7` | [0, 0], [2, 4] |
| 3 | 2 | [2, 4] | 2 | 2 | `1 2 (2) 5 2 6 9 7` | [2, 1], [3, 4] |
| 4 | 3 | [3, 4] | 2 | 3 | `1 2 2 (2) 5 6 9 7` | [3, 2], [4, 4] |
| 5 | 1 | [6, 7] | 7 | 6 | `1 2 2 2 5 6 (7) 9` | [6, 5], [7, 7] |

Шаги 2-4 показывают повторы: каждая двойка - pivot своего шага, остальные двойки при сравнении
`<` уходят вправо, и каждый раз левый отрезок пуст или из одного элемента.

### Плохой вход для quick_sort: `[1, 2, 3, 4, 5, 6]`

| Шаг | Глубина | Отрезок | pivot | p | Массив после partition | Дальше |
|---|---|---|---|---|---|---|
| 1 | 0 | [0, 5] | 6 | 5 | `1 2 3 4 5 (6)` | [0, 4], [6, 5] |
| 2 | 1 | [0, 4] | 5 | 4 | `1 2 3 4 (5) 6` | [0, 3], [5, 4] |
| 3 | 2 | [0, 3] | 4 | 3 | `1 2 3 (4) 5 6` | [0, 2], [4, 3] |
| 4 | 3 | [0, 2] | 3 | 2 | `1 2 (3) 4 5 6` | [0, 1], [3, 2] |
| 5 | 4 | [0, 1] | 2 | 1 | `1 (2) 3 4 5 6` | [0, 0], [2, 1] |

Pivot каждый раз максимум, правый отрезок пустой, левый короче на 1: глубина растет до `n - 2`,
сравнений `5 + 4 + 3 + 2 + 1 = 15 = n(n - 1)/2`. `merge_sort` на том же массиве делит его пополам,
глубина `ceil(log2 6) = 3`.

## Сравнение производительности

**Гипотеза.** На случайных данных обе сортировки работают за Θ(n log n). На отсортированном,
обратном и постоянном массивах `quick_sort` с pivot = последний элемент переходит в Θ(n²), а
`merge_sort` остается Θ(n log n), поэтому разница должна расти примерно пропорционально
`n / log n`.

**Условия.**

- Виды входов: `random` (`randrange(10 n)`, seed 6), `sorted` (`0..n-1`), `reversed`
  (`n..1`), `equal` (`n` семерок).
- Размеры 100, 300, 900 для всех видов. Больше 900 для вырожденных входов брать нельзя: глубина
  рекурсии `quick_sort` там около `n`, а предел - 1000 кадров. Для случайных дополнительно 10 000
  и 100 000.
- Массив строится один раз до замеров, обе сортировки получают один и тот же объект (вход они не
  меняют). Генерация и проверка результата через `sorted()` в замер не входят.
- 7 запусков, сортировки чередуются (merge, quick, merge, quick, ...), чтобы фоновая нагрузка
  влияла на обе одинаково. В таблице медиана `last_time` из декоратора `timer`.
- Копирование входа входит в время обеих сортировок: обе возвращают новый список.

Результат одного запуска `python main.py` (Python 3.13, Linux, Intel Xeon 2.1 ГГц). На другой
машине числа будут другими, но соотношения похожими.

| Массив | n | merge_sort, мс | quick_sort, мс | quick / merge |
|---|---|---|---|---|
| random | 100 | 0.12 | 0.05 | 0.5 |
| random | 300 | 0.37 | 0.17 | 0.5 |
| random | 900 | 1.03 | 0.57 | 0.6 |
| sorted | 100 | 0.06 | 0.24 | 3.9 |
| sorted | 300 | 0.21 | 2.07 | 9.8 |
| sorted | 900 | 0.72 | 21.34 | 29.8 |
| reversed | 100 | 0.07 | 0.18 | 2.6 |
| reversed | 300 | 0.22 | 1.61 | 7.2 |
| reversed | 900 | 0.68 | 14.57 | 21.5 |
| equal | 100 | 0.06 | 0.11 | 1.9 |
| equal | 300 | 0.19 | 0.91 | 4.9 |
| equal | 900 | 0.62 | 7.99 | 13.0 |
| random | 10000 | 12.19 | 7.14 | 0.6 |
| random | 100000 | 193.04 | 117.70 | 0.6 |

**Выводы.**

- На случайных данных `quick_sort` здесь быстрее в 1.7-2 раза: он переставляет элементы на
  месте, а `merge_sort` на каждом уровне создает новые списки (срезы и результаты `merge`) и
  делает `append` по одному элементу. Асимптотика одинаковая, отличается константа.
- На `sorted`, `reversed` и `equal` все наоборот, и отставание `quick_sort` растет с `n`: при
  увеличении `n` в 3 раза (300 -> 900) его время растет в 9-10 раз, как и должно быть у Θ(n²), а
  время `merge_sort` - в 3.1-3.4 раза. При `n = 900` `quick_sort` делает
  `n(n - 1)/2 = 404 550` сравнений против не более `n * ceil(log2 n) = 9 000` у `merge_sort`.
- Все три вырожденных входа дают одинаковое число сравнений, разница между ними - в числе обменов.
  На `sorted` каждый элемент меньше pivot, и обмен выполняется на каждой итерации (элемента с самим
  собой). На `equal` условие `arr[j] < pivot` не выполняется ни разу, в цикле обменов нет, поэтому
  этот случай самый быстрый из трех.

Значит, ни одна из сортировок не быстрее всегда: результат зависит от входа. Проблему
`quick_sort` убирает выбор pivot, не зависящий от порядка (средний или случайный элемент), а
повторы - трехчастное разбиение, как в задаче 3.
