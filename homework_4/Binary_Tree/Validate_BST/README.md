# Задача 2. Validate BST

Дано произвольное бинарное дерево. Нужно проверить, является ли оно корректным деревом поиска
(BST), и вернуть `True` или `False`.

Определение. Условие не говорит, как быть с равными значениями, поэтому используется то же
определение BST, что и в задаче 1 (Tree Traversal), – оно общее для обеих задач:

> для каждого узла все значения его левого поддерева **строго меньше** значения узла,
> а все значения правого поддерева **больше либо равны** ему: `left < node <= right`.
> Ограничение действует относительно всех предков, а не только родителя.

Повторы допустимы, но только справа: дерево `5 -> правый 5` корректно, `5 -> левый 5` – нет.
Именно такие деревья строит вставка из задачи 1 (равное значение уходит вправо), поэтому любое
дерево, построенное там, здесь признается корректным. Пустое дерево считается BST.

## Объяснение решения

### Почему не хватает сравнения с детьми

```
       10
      /  \
     5    15
         /  \
        6    20
```

Каждый узел правильно расположен относительно своего родителя, но 6 лежит в правом
поддереве корня 10, а должно быть больше 10. Значит на узел действуют ограничения от всех
предков, а не только от родителя.

### Идея: допустимый интервал

Каждому узлу сопоставим полуинтервал `[low, high)`, в который обязано попасть его значение:

- у корня ограничений нет: `(None, None)`, где `None` значит "границы нет";
- левый ребенок узла `v` с границами `low, high` получает `[low, v)`: сверху добавляется
  строгая граница `v`, нижняя наследуется;
- правый ребенок получает `[v, high)`: снизу добавляется нестрогая граница `v`, верхняя
  наследуется.

Проверка узла – это `low <= value < high` (отсутствующая граница не проверяется). Строгость
границы определяется тем, с какой стороны от предка лежит узел, и сохраняется на любой глубине:

- верхнюю границу всегда задает предок, в **левом** поддереве которого лежит узел, поэтому она
  строгая. Повтор такого предка ловится, даже если до него несколько уровней
  (`5 -> левый 3 -> правый 5` некорректно);
- нижнюю границу всегда задает предок, в **правом** поддереве которого лежит узел, поэтому она
  нестрогая. Повтор такого предка допустим, тоже на любой глубине
  (`5 -> правый 8 -> левый 5` корректно).

Отдельно хранить признак строгости не нужно: у `low` он всегда "нестрогая", у `high` – "строгая".

`None` вместо числовых "бесконечностей" выбран намеренно: константа вроде `-10**9` выглядела бы
как граница и отвергла бы допустимое значение `-10**12`. Целые в Python не ограничены, поэтому
честного "минус бесконечности" среди них нет.

### Реализация

Обход в глубину с явным стеком, в котором лежат тройки `(узел, low, high)`. Достаем тройку,
проверяем узел; если проверка не прошла, сразу ответ `False`. Иначе кладем детей с их
интервалами: сначала правого, потом левого, чтобы левое поддерево проверялось раньше (порядок
на ответ не влияет, но так трассировку удобнее читать – это прямой обход).

Сам обход написан как генератор `check_steps(root)`: он выдает `(node, low, high, ok)` для
каждого проверенного узла и останавливается после первого `ok == False`.
`is_valid_bst` – это `all(ok for ...)` по этому генератору: `all` прекращает чтение на первом
`False`, а для пустого дерева генератор ничего не выдает и `all` дает `True`. Тот же генератор
используется в визуализации ниже, так что таблица и решение не могут разойтись.

Дерево не меняется: из узлов только читаются `value`, `left`, `right`.

### Почему итеративно, а не рекурсивно

Рекурсивная версия короче на пару строк, но глубина рекурсии равна высоте дерева. Для цепочки из
3000 узлов (а это обычное несбалансированное дерево, например после вставки отсортированных
значений) она упадет с `RecursionError` при стандартном лимите в 1000. Стек на списке ограничен
только памятью, и `sys.setrecursionlimit` трогать не нужно. Тест `test_deeper_than_recursion_limit`
проверяет цепочку длиной в 3 раза больше лимита.

### Почему интервалы, а не inorder

Второй стандартный способ: симметричный обход BST дает неубывающую последовательность. С
повторами одной неубываемости уже мало: деревья `5 -> левый 5` и `5 -> правый 5` дают один и тот
же обход `5, 5`, а корректно только второе. Нужно еще помнить, из какого поддерева пришло
предыдущее значение: если узел имеет левое поддерево, перед ним в обходе стоит максимум этого
поддерева, и он должен быть строго меньше узла. Кроме того, в простом виде способ собирает все
значения в список (O(n) памяти), а без списка нужно хранить предыдущее значение и аккуратно
обходить дерево итеративно в симметричном порядке, что заметно менее прозрачно. Метод интервалов
напрямую повторяет определение BST, и по таблице шагов видно, какой предок задал нарушенную
границу. Inorder с этой поправкой используется в тестах как второй независимый эталон.

## Корректность

**Инвариант.** Когда узел со значением `x` достается из стека, условие `low <= x < high` равносильно
всем ограничениям, которые на него накладывают предки: `x < a` для каждого предка `a`, в левом
поддереве которого он лежит, и `x >= a` для каждого предка `a`, в правом поддереве которого он
лежит. При этом `low` – наибольшее значение среди предков второго вида, `high` – наименьшее среди
предков первого вида (`None`, если таких предков нет).

Почему инвариант верен:

1. У корня предков нет, и в стек он кладется с `(None, None)`.
2. Переход в левое поддерево узла `v` добавляет ровно одно новое ограничение: `x < v`. В коде
   `high` заменяется на `v`. Старое `high` можно отбросить: до этого шага узел `v` сам прошел
   проверку `v < high`, значит из `x < v` следует `x < high`.
3. Переход вправо: добавляется `x >= v`, и `low = v`. Старое `low` можно отбросить: `v` прошел
   проверку `low <= v`, значит из `x >= v` следует `x >= low`. Здесь важно, что обе границы
   сравниваются правильно: нестрогое `low <= v` вместе с нестрогим `x >= v` дает нестрогое
   `x >= low` – ровно то ограничение, которое задавал старый предок.
4. Вторая граница передается без изменений, поэтому ограничения, заданные выше, сохраняются на
   любой глубине вместе со своей строгостью. Например, в примере ниже граница `high = 15` от
   корня доходит до узла 16 через два уровня, а в примере с повторами строгая граница `high = 29`
   от первого 29 доходит до второго 29 через узел 26.

**Если возвращается `False`, дерево не BST.** Узел не попал в свой интервал, то есть нарушил
ограничение какого-то конкретного предка `a`: лежит в левом поддереве `a`, но не меньше его
(в том числе равен ему), или в правом, но меньше его. Это прямое нарушение определения.

**Если возвращается `True`, дерево BST.** Тогда проверены все узлы: каждый, прошедший проверку,
кладет в стек своих детей, и обход заканчивается только когда стек пуст. По инварианту каждый
узел удовлетворяет ограничениям всех своих предков. Возьмем любой узел `v` и любой `x` из его
левого поддерева: `v` – предок `x`, и `x` в левом поддереве `v`, значит `x < v`. Для правого
поддерева так же получаем `x >= v`. Это и есть определение BST.

## Оценка сложности

Обозначения: `n` – число узлов, `h` – высота дерева (число уровней).

| | время | дополнительная память |
|---|---|---|
| худший случай | O(n) | O(h) |
| сбалансированное дерево | O(n) | O(log n) |
| цепочка | O(n) | O(n) |

### Время

Каждый узел попадает в стек один раз (его кладет только родитель) и проверяется один раз:
два сравнения и до двух `append`. Итого O(n). Разрешение повторов справа на оценку не влияет:
изменился только знак одного сравнения (`low <= value` вместо `low < value`), число шагов и
содержимое стека те же. При нарушении обход останавливается раньше, в
примере ниже из 9 узлов проверено 6. Но для корректного BST нужно посмотреть все узлы:
непроверенный узел мог бы оказаться любым, поэтому O(log n), как у поиска в BST, здесь не
получить.

### Память

Значения в отдельный список не собираются, память уходит только на стек троек. Рекурсии нет.

В стеке лежат отложенные правые дети на пути от корня к текущему узлу – не больше одного на
уровень, плюс два ребенка только что проверенного узла на следующем уровне. Корень вместе с
другими узлами в стеке не бывает, поэтому записей не больше `h`, то есть O(h). Я дополнительно
замерил размер стека на 3000 случайных деревьях: число уровней он ни разу не превысил.

Сколько это в `n`, зависит от формы дерева:

- у сбалансированного дерева на каждом уровне примерно вдвое больше узлов, чем на предыдущем,
  поэтому уровней около `log2 n`, и память O(log n);
- у цепочки (каждый узел имеет одного ребенка) `h = n`, и память O(n).

Дерево произвольное, его форма не гарантирована, поэтому без оговорок можно сказать только O(h),
а в худшем случае O(n). Входное дерево в эту оценку не входит.

## Визуализация

### Некорректное дерево

```
            15
          /    \
         8      23
        / \    /  \
       4   12 17   30
          /  \
        10    16   <- нарушение: 16 > 12, но лежит в левом поддереве 15
```

Узел 16 правильно стоит относительно родителя 12, поэтому проверка только с детьми этого не
заметит. Дерево строит `readme_tree()` в тестах, а таблицу целиком сверяет тест
`TestReadmeTrace.test_invalid_tree_steps`.

В стеке хранятся тройки `(узел, low, high)`, записанные как `узел [low, high)`; вершина стека
справа, `–` значит `None`.

| Шаг | Узел | low | high | Проверка | Стек после шага |
|---:|---:|---:|---:|---|---|
| 1 | 15 | – | – | нет границ, ok | `23 [15, –)`, `8 [–, 15)` |
| 2 | 8 | – | 15 | 8 < 15, ok | `23 [15, –)`, `12 [8, 15)`, `4 [–, 8)` |
| 3 | 4 | – | 8 | 4 < 8, ok | `23 [15, –)`, `12 [8, 15)` |
| 4 | 12 | 8 | 15 | 8 <= 12 < 15, ok | `23 [15, –)`, `16 [12, 15)`, `10 [8, 12)` |
| 5 | 10 | 8 | 12 | 8 <= 10 < 12, ok | `23 [15, –)`, `16 [12, 15)` |
| 6 | 16 | 12 | 15 | **16 < 15 неверно** | обход прекращен, ответ `False` |

Что здесь видно:

- граница `high = 15` появляется на шаге 2 при переходе влево от корня и без изменений
  передается в 12 (шаг 4) и в 16 (шаг 6) – через два уровня;
- на шаге 4 при переходе вправо от 8 нижняя граница стала 8, а верхняя 15 сохранилась;
- у узла 10 (шаг 5) верхняя граница уже 12, она строже 15 – так и работает пункт 2 доказательства;
- пока проверяется левое поддерево, `23 [15, –)` лежит на дне стека и ждет своей очереди.

Почему `False`: узел 16 должен быть меньше 15, потому что он в левом поддереве корня, а
16 >= 15. Это нарушение определения BST относительно корня, и правое поддерево (23, 17, 30) уже
не проверяется.

### Корректное дерево

```
         8
       /   \
      3     10
     / \      \
    1   6      14
```

| Узел | 8 | 3 | 1 | 6 | 10 | 14 |
|---|---|---|---|---|---|---|
| интервал | `[–, –)` | `[–, 8)` | `[–, 3)` | `[3, 8)` | `[8, –)` | `[10, –)` |

Все шесть узлов попадают в свои интервалы, стек опустошается, ответ `True`. Например, 6
проверяется не только против родителя 3, но и против корня: интервал `[3, 8)`. Эту строку
сверяет тест `test_valid_tree_steps`.

### Дерево с повтором

Возьмем дерево из визуализации задачи 1: вставки `41, 20, 65, 11, 29, 91, 32, 72, 26, 29`.
Второе 29 обозначено `29'`, в дереве это обычное 29.

```
                41
             /      \
           20        65
          /  \         \
        11    29        91
             /  \       /
           26    32   72
                /
              29'
```

| Узел | 41 | 20 | 11 | 29 | 26 | 32 | 29' | 65 | 91 | 72 |
|---|---|---|---|---|---|---|---|---|---|---|
| интервал | `[–, –)` | `[–, 41)` | `[–, 20)` | `[20, 41)` | `[20, 29)` | `[29, 41)` | `[29, 32)` | `[41, –)` | `[65, –)` | `[65, 91)` |

Ответ `True`. Ключевой узел – `29'`: нижнюю границу 29 он получил от первого 29 (лежит в его
правом поддереве), и проверка `29 <= 29 < 32` проходит именно потому, что нижняя граница
нестрогая. При старом строгом определении здесь был бы ответ `False`, и задачи 1 и 2 расходились
бы: дерево, построенное вставкой из задачи 1, не проходило бы проверку задачи 2. Таблицу сверяет
тест `test_duplicate_tree_steps`.

### Повтор, нарушающий границу предка

То же дерево, но второе 29 подвешено правым ребенком к 26:

```
                41
             /      \
           20        65
          /  \         \
        11    29        91
             /  \       /
           26    32   72
             \
              29'   <- нарушение: 29' в левом поддереве первого 29, а там нужно < 29
```

С родителем все в порядке (`29' >= 26`, это правый ребенок), но первое 29 – предок, и `29'`
лежит в его левом поддереве, где равные значения запрещены.

| Шаг | Узел | low | high | Проверка | Стек после шага |
|---:|---:|---:|---:|---|---|
| 1 | 41 | – | – | нет границ, ok | `65 [41, –)`, `20 [–, 41)` |
| 2 | 20 | – | 41 | 20 < 41, ok | `65 [41, –)`, `29 [20, 41)`, `11 [–, 20)` |
| 3 | 11 | – | 20 | 11 < 20, ok | `65 [41, –)`, `29 [20, 41)` |
| 4 | 29 | 20 | 41 | 20 <= 29 < 41, ok | `65 [41, –)`, `32 [29, 41)`, `26 [20, 29)` |
| 5 | 26 | 20 | 29 | 20 <= 26 < 29, ok | `65 [41, –)`, `32 [29, 41)`, `29' [26, 29)` |
| 6 | 29' | 26 | 29 | **29 < 29 неверно** | обход прекращен, ответ `False` |

Строгая граница `high = 29` появилась на шаге 4 при переходе влево от первого 29 и дошла до
`29'` через узел 26, у которого `29'` – правый ребенок. Таблицу сверяет тест
`test_bad_duplicate_tree_steps`.

## Тесты

`test_validate_bst.py`, 38 тестов в семи классах. Запуск: `python -m unittest -v`.

Все эталоны используют то же определение `left < node <= right`, что и решение.

| Класс | Что проверяется |
|---|---|
| `TestBasic` | пустое дерево, один узел, два узла (корректные и нет), многоуровневое BST, нарушение у корня, глубокие нарушения в левом и правом поддеревьях, корректное несбалансированное дерево, оба дерева из README; результат сравнивается через `assertIs(..., True/False)`, то есть возвращается именно `bool` |
| `TestAncestors` | 7 деревьев, на которых проверка только с родителем ошибается: тест сначала убеждается, что ошибочная `parents_only` их принимает, а эталон отвергает, и только потом проверяет решение; нарушения от корня и от промежуточного предка, слева и справа, на глубине до 4 уровней; значение, равное значению далекого предка: в его левом поддереве некорректно, в правом – корректно |
| `TestEdgeCases` | отрицательные числа и ноль, числа порядка `10**30` и `sys.maxsize + 1`, цепочки только из левых и только из правых детей, зигзаг, цепочка в 3 раза длиннее лимита рекурсии; на той же цепочке – обе границы на глубине: значение, равное нижней границе от далекого предка, допустимо, а равное верхней (родителю) – нет |
| `TestDuplicates` | повтор справа от корня – корректно; повтор слева от корня – нет; правая цепочка равных значений (в том числе построенная вставкой `7 7 7 ...` как в задаче 1) и цепочка `1 1 2 2 2 3` – корректны; левая цепочка равных – нет; повторы во вложенных поддеревьях, корректные относительно всех предков (дерево из задачи 1 со вторым 29); повторы, нарушающие строгую границу предка через несколько уровней (`5 -> 3 -> правый 5`, второе 29 под 26, повтор корня на глубине 4); цепочка равных, которая корректна, пока не дойдет до значения предка; деревья с повторами, на которых проверка только с родителем ошибается; пустое дерево, один узел, дерево без повторов |
| `TestNoSideEffects` | после проверки те же объекты узлов, те же значения и те же объекты детей (`assertIs`); повторные и чередующиеся вызовы на разных деревьях дают те же ответы; недочитанный генератор не влияет на следующие проверки |
| `TestRandom` | фиксированные seed. Эталон `oracle` проверяет определение напрямую: для каждого узла сравнивает его со всеми значениями обоих поддеревьев (`<` слева, `>=` справа), O(n²). 300 случайных BST без повторов; 300 деревьев из вставок как в задаче 1 со значениями от -5 до 5 – много повторов, все должны быть корректны; 500 BST с одним измененным значением, где ответ берется у эталона, а не предполагается `False` (некорректными оказываются больше 100 из них); 2000 произвольных деревьев с повторами и отрицательными значениями, где решение сверяется с `oracle`, а `oracle` – со вторым эталоном на inorder (неубывание и строгое `<` перед узлом с левым поддеревом); инварианты шагов: каждый узел проверен не больше раза, `ok` равно `low <= value < high`, при `True` проверены все узлы |
| `TestReadmeTrace` | все четыре таблицы визуализации целиком, включая обе с повтором |

Дополнительно я проверил сами тесты на ошибочных версиях решения: со старым строгим сравнением
(`low < value < high`, повторы запрещены) падает 12 тестов, с нестрогим с обеих сторон
(`low <= value <= high`) – 10, с перепутанной строгостью (`low < value <= high`) – 16,
с проверкой только относительно родителя – 21. Отдельно сверил задачи между собой: 5000
